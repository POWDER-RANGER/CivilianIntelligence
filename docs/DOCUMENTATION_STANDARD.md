# Repository Documentation Standard

**Scope:** all repositories in the CIVWATCH ecosystem.  
**Documentation authority:** this repository is the system of record for the unified application and its cross-repository integration contract.

## Source of truth

- **Current service health and public URLs:** the [CIVWATCH status page](https://powder-ranger.github.io/CIVWATCH/status.html) and fresh service probes. A repository README or old status snapshot is not live-health evidence.
- **Application architecture and service boundaries:** [Cross-repository integration contract](./CROSS_REPO_INTEGRATION.md).
- **Repository purpose and local setup:** each repository's own README and actively maintained setup guide.
- **Historical plans and audit notes:** retained for context, clearly dated and not presented as current deployment or acceptance evidence.

Avoid copying the same platform overview or roadmap into every repository. Keep each README focused on that repository's purpose, prerequisites, supported commands, verified status, and links to the canonical contract.

## AI-tool attribution and generated artifacts

- Do not add agent-session URLs, chat transcripts, automatic “Generated with …” footers, or links to externally hosted AI-generated reports to maintained project documentation.
- Do not attribute project ownership, code authorship, or product endorsement to an AI tool. When an explicit AI-tool acknowledgement is genuinely required and supported by the record, AI-tool credits are limited to **Anthropic** and **OpenAI** and must be accurate and narrowly worded.
- Keep generated files, assets, and other repository artifacts intact unless a separate engineering change explicitly calls for their removal. A generated file is not to be deleted simply to remove an attribution or a documentation link.
- Keep deterministic generator instructions when they are needed to maintain the repository, for example a source file generated by TanStack Router or a design-token build script. These are build-maintenance notes, not AI-tool credits.
- Preserve required open-source licence notices, copyright statements, upstream code provenance, public-data attribution, and source citations. These legal and data-provenance obligations are separate from AI-tool accreditation and must not be removed by this policy.
- Keep real integration documentation that names an upstream service or runtime when that reference is technically necessary; this policy targets credits and editorial noise, not functional configuration.

## Writing and maintenance rules

1. Keep one canonical explanation for each architecture, API contract, deployment procedure, and operational runbook; link to it rather than copying it.
2. Use concise repository READMEs. Put detailed implementation and incident history in a specifically named reference document.
3. Date snapshots and label them **historical** when they no longer describe the current branch or deployment.
4. State only what repository state, tests, logs, live probes, or authoritative sources verify. Distinguish implemented, configured, live, degraded, and planned states.
5. Keep examples executable and safe. Use unmistakable placeholders for secrets; never include working credentials, tokens, or private user data.
6. Do not delete source assets, generated outputs, licence records, or historical evidence as a shortcut for documentation cleanup.

## Documentation review checklist

- [ ] Is there one canonical source for this information?
- [ ] Are current-status claims dated and backed by verifiable evidence?
- [ ] Have copied status blurbs, stale roadmaps, and repeated explanations been removed or replaced by links?
- [ ] Are AI-agent footers, session links, and external AI-generated-report links absent?
- [ ] Are Anthropic/OpenAI credits, if present, accurate and limited to those providers?
- [ ] Are legally required software licences, upstream provenance, and data-source attributions preserved?
- [ ] Were the underlying files preserved unless a separate technical change required otherwise?
